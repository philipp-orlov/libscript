# Embedding

```cpp
#include "script/script.hpp"

script::Context ctx;
script::Value a = ctx.eval("return 6 * 7;", "<eval>", script::Language::CSharp);
script::Value b = ctx.eval("6 * 7", "answer.js");   // the extension picks JavaScript
```

Link against `script::script`. The whole public API is `script/script.hpp`
and the namespace `script`; nothing under `script/internal/` is part of it.
`script/config.hpp` is generated by the build and says which languages it
contains (`SCRIPT_LANG_CSHARP`, `SCRIPT_LANG_TYPESCRIPT`,
`SCRIPT_LANG_JAVASCRIPT`, `SCRIPT_ENGINE_TYPED`, `SCRIPT_ENGINE_DYNAMIC`,
`SCRIPT_ENABLE_JIT`, each 0 or 1).

## The context

One `Context` is one heap, one lock, and one runtime per engine, created the
first time a language needs it. Contexts share no global state, so the way to
get parallelism is one per thread. Every public entry point takes the lock, so
a context may also be shared and calls are serialized; `Context::Lock` holds it
across several operations.

```cpp
script::Context::Options options;
options.memoryLimit = 64u << 20;         // bytes; 0 means unbounded
options.stackLimit  = 512;               // maximum call depth, across every language
options.gcThreshold = 4u << 20;          // heap growth between cycle collections
options.threadSafe  = true;              // take the lock on every entry point
options.language    = script::Language::TypeScript;   // when a source name does not say
options.compile.checkedArithmetic = true;              // C#
options.compile.native = true;                         // C#: machine code where possible
options.jit.mode = script::JitOptions::Mode::Tiered;  // C#: or compile only what gets hot
options.check = script::CheckOptions::strict();       // TypeScript: strictNullChecks, noImplicitAny
options.runtimeCode = false;                          // JavaScript: eval and new Function stay EvalErrors (the default)
script::Context ctx(options);
```

### Running code you did not write

Source from outside is safe to compile and run -- it cannot reach the file system, the network or the host's memory --
but nothing limits what it *costs* until the host says so. Out of the box a context has no memory ceiling and no time
limit, so set both before running anything untrusted:

```cpp
options.memoryLimit = 64u << 20;                  // the ceiling for what the program holds, in bytes
script::Context ctx(options);
const auto deadline = std::chrono::steady_clock::now() + std::chrono::seconds(2);
ctx.setInterruptHandler([=] { return std::chrono::steady_clock::now() > deadline; });   // timeouts, cancellation
```

* **Memory.** `memoryLimit` is checked before a cell is made and before a container grows, so one huge request
  (`new Array(1e9)`, `x.repeat(1e9)`, `new int[int.MaxValue]`, `a = a.concat(a)`) is refused with
  `Error(OutOfMemory)` rather than allocated and then noticed. The figure counts what the heap holds; the process
  also pays for the allocator's own overhead and for temporaries inside a builtin, so allow it some headroom.
* **Time.** The handler is called about every 4096 instructions in the interpreters, every 1024 loop iterations in
  native code, and inside builtins that loop over a size the program chose (`Array.from({length: n})`, `join`). It runs
  on the thread that runs the program; keep it cheap, as it reads a clock in the usual case. A native host function
  that blocks is not interrupted.
* **Stack.** `stackLimit` counts script frames. The engine also looks at the thread's real stack, so a worker thread
  with a small stack gets `Error(StackOverflow)` -- or a compile error for deeply nested source -- instead of a
  crash. Budget about 1 MiB of native stack for the default limit of 512 frames in JavaScript, TypeScript and Python
  (about 512 KiB in C#, C and C++), and keep 96 KiB free below that for the compiler.
* **Source shape.** The front ends refuse source that nests expressions deeper than 500 levels, or chains more than
  2000 operators or member accesses in one expression (`a + b + c + ...`, `a.b.c...`). `JSON.parse` and
  `JSON.stringify` stop at 1000 levels, and `JSON.stringify` reports a cycle as a `TypeError`.
* **Images** (`Assembly::serialize`, `Context::load`) are trusted input, but they carry a checksum: an image that was
  cut short or damaged in storage is refused with `Error(BadImage)` instead of running as damaged bytecode.

**A `Value` belongs to its context and must not outlive it.** Destroying a
context invalidates every value from it. The one exception is a
`script::Exception`, which may unwind out of the scope that owned the
context; see [Errors](#errors).

## Choosing a language

Every compile and run entry point takes a `Language` last, defaulting to
`Language::Auto`. `Auto` decides in this order:

1. the extension of the source name -- `.cs`; `.ts`, `.mts`; `.js`, `.mjs`,
   `.cjs`; `.py`; `.c`, `.h`; `.cpp`, `.cc`, `.cxx`, `.hpp`, `.hh`, `.hxx`
   (`script::languageOfFile` is the same rule);
2. `Options::language`;
3. the first language this build contains, in the order C#, TypeScript,
   JavaScript, Python, C, C++.

So a polyglot host names its files, a single-language host sets the option
once, and a C#-only build needs neither. A language the build lacks throws
`Error(NotSupported)` rather than falling back to another one.

```cpp
script::supported(script::Language::TypeScript);   // does this build have it?
script::supportedLanguages();                        // every language, in Auto's order
script::languageNamed("cs");                         // "csharp", "cs", "c#", "ts", ".js" ...
script::toString(script::Language::CSharp);         // "csharp"
```

## Compiling and running

```cpp
script::Assembly rules = ctx.compile(source, "rules.cs");   // throws CompileError
script::Value verdict = ctx.run(rules);                     // runs the entry point
script::Value sum = ctx.call(rules, "Math2.Add", {script::Value(2), script::Value(3)});

script::Assembly plugin = ctx.compile(source, "plugin.js");
ctx.run(plugin);                                             // as often as you like
```

`eval` is `compile` plus `run`, and `evalFile`/`compileFile` read the file
first. An `Assembly` is any language's compiled program; `assembly.language()`
says which. `run` runs the C# entry point, or the whole TypeScript or
JavaScript program in the global scope, returning what `Main` returned or the
completion value of the last statement. `call` names a method in a C#
assembly and picks the overload from the arguments.

To report instead of throw:

```cpp
script::Assembly assembly;
for (const script::Diagnostic& d : ctx.diagnose(source, "rules.ts", &assembly))
    std::puts(d.toString().c_str());        // rules.ts(3): error: ...
if (assembly)
    ctx.run(assembly);
```

A syntax error still throws `Error(SyntaxError)`, because there is no program
to report on. Diagnostics carry `language`, `file`, `line`, `column` (0 when
the language does not say), `code` (the C# number, 0 for TypeScript) and
`message`; `toString()` prints `prog.cs(2,5): error CS0029: ...` or
`rules.ts(3): error: ...`.

C# assemblies serialize to a portable image and load again without parsing;
`serialize()` on a TypeScript or JavaScript assembly throws
`Error(NotSupported)`. C# programs may be several units compiled in dependency
order. See [compilation.md](compilation.md). `compileNative` and `jitBackend`
are the machine-code switches; see [jit.md](jit.md).

Top-level TypeScript and JavaScript declarations land on the global object and
persist, so successive evaluations see each other:

```cpp
ctx.eval("const config = { retries: 3 };", "a.js");
int retries = ctx.eval("config.retries", "b.js").as<int>();
ctx.global();                                  // the global object itself
```

## Values

`script::Value` is a 16-byte tagged union. Primitives live inline; strings,
symbols, objects, arrays and functions are counted references, so copying a
`Value` is a refcount bump and holding one keeps the referent alive across
collections. The tags:

| `Type` | Made by | Tests |
| --- | --- | --- |
| `Undefined` | JavaScript, `Value::undefined()` | `isUndefined()`, `isNullish()` |
| `Null` | `Value()`, `Value(nullptr)`, C# `null`, JavaScript `null` | `isNull()`, `isNullish()` |
| `Bool`, `Char`, `Int`, `Long`, `Float`, `Double` | the constructors, C# | `isBool()`, `isChar()`, `isNumber()` (Int .. Double) and one test per tag |
| `Double` | every JavaScript number | `isDouble()` |
| `String` | `ctx.str()`, both languages | `isString()` |
| `Symbol` | `ctx.symbol()`, JavaScript | `isSymbol()` |
| `Object` | a C# instance, a host wrapper, any JavaScript object | `isObject()`, plus `isArray()`, `isFunction()`, `isError()`, `isPromise()`, `isNative()` which look at the cell |
| `Array`, `Delegate` | C# arrays and delegates | `isArray()`, `isFunction()` |

`isReference()` is true for everything from `String` on. `typeName()` is the
C# type name (`"System.Int32"`, `"Geometry.Point"`) or `"object"`,
`"function"`, `"string"` for the dynamic side. `context()` is the owning
context, or null for a primitive.

Conversions:

```cpp
v.toBool();     // truthiness: false for null, undefined, false, 0, NaN, ""
v.toInt();      // ECMAScript ToInt32 for doubles; a JavaScript object goes through valueOf
v.toLong();
v.toDouble();   // NaN for undefined; a string parses
v.toString();   // ToString(), possibly running the program's own override
v.inspect();    // for logs: strings quoted, objects one level deep
v.toJson(2);    // JSON.stringify for JavaScript values and primitives
```

A primitive with no heap behind it prints the way JSON would, whichever
language it came from: `true`, `null`, `undefined`, `42`, `1e+21`,
`0.30000000000000004`. A heap value prints the way its language does --
`true.ToString()` inside C# is still `"True"`.

Three equalities:

| Call | Meaning |
| --- | --- |
| `a.sameReference(b)` | the same cell, or equal primitives of the same tag |
| `a.strictEquals(b)`, `a == b` | `===`: numbers by value whatever their tag, strings by content, the rest by identity |
| `a.equals(b)` | the language's own: `Object.Equals` for a C# value, `==` for a JavaScript one |

Members work on whatever the value is:

```cpp
script::Value point = ctx.newObject(assembly, "Point", {script::Value(1), script::Value(2)});
point.get("X");                       // a C# field or property
point.set("Y", 10);                   // converts, thanks to binding.hpp
point.invoke("Sum");                  // a C# method; the overload fits the arguments
point.keys();                         // field and property names, base first
point.has("X");

script::Value o = ctx.eval("({ name: 'x', tags: ['a', 'b'] })", "o.js");
o.get("tags").get(1u).toString();     // a JavaScript property, an element
o.keys();                             // own enumerable keys, insertion order
o.get("tags").length();               // 2
o.get("tags").push(ctx.str("c"));     // also appends to a C# List<T>
o.hasOwn("name"); o.remove("name");   // JavaScript only
o.defineProperty("k", v, script::PropertyFlags::ReadOnly);
o.defineAccessor("k", getter, setter);
o.prototype(); o.setPrototype(proto);

script::Value array = ctx.newArray(script::Type::Int, 16);   // a C# int[16]
array.set(0u, script::Value(7));
ctx.newArray("Geometry.Point", 4);                              // by C# type name
```

The index overloads take `std::uint32_t`; write `get(0u)`, not `get(0)`,
which is ambiguous with the `const char*` and `Value` overloads.

Callables:

```cpp
script::Value fn = ctx.eval("(a, b) => a * b", "f.js");
fn(6, 7).toDouble();                              // arguments are converted
fn.call({script::Value(6), script::Value(7)});  // explicit values
fn.callWithThis(receiver, args);                  // JavaScript `this`
ctor.construct({script::Value(1)});              // new ctor(1), JavaScript
script::Value even = ctx.call(assembly, "Filters.Even");
even(4).toBool();                                 // a C# delegate, called from C++
auto multiply = ctx.as<std::function<int(int, int)>>(fn);
```

## Conversions

`ctx.value(x)` goes C++ to script, `ctx.as<T>(v)` and `v.as<T>()` come back.
Out of the box: `bool`, `char16_t`, the sized integers, `float`, `double`,
enums, `std::string`, `std::string_view`, `const char*`, `script::Value`,
`std::optional<T>`, `std::vector<T>`, `std::map` and `std::unordered_map` keyed
by string, `std::function<R(A...)>`, `T*`, `std::shared_ptr<T>` and `T` by
value for any class bound with `Class<T>`.

Integers convert to `Int` or `Long`, floating point to `Float` or `Double`,
so a C# method sees the type its signature promised and a JavaScript program
sees a number. `std::vector<T>` builds a JavaScript array on its way in and
reads any array -- JavaScript or C# -- on its way out; `std::map` and
`std::function` build JavaScript objects and functions, and read JavaScript
objects and any callable. In a C#-only build the JavaScript-shaped
constructions throw `Error(NotSupported)`.

Teach it a new type by specializing `script::Convert`:

```cpp
template <>
struct script::Convert<std::chrono::seconds>
{
    static script::Value to(script::Context&, std::chrono::seconds s)
    {
        return script::Value(double(s.count()));
    }
    static std::chrono::seconds from(script::Context&, const script::Value& v)
    {
        return std::chrono::seconds(v.toLong());
    }
};
```

## Exposing the host

A static class of functions. Each member is declared once; the C# compiler and
the TypeScript checker type-check the calls from the C++ signature, and
JavaScript finds the same functions on a global object of the same name:

```cpp
ctx.hostClass("Env")
   .method("Now", [] { return std::time(nullptr); })
   .method("Log", [](std::string message) { std::puts(message.c_str()); })
   .method("Hypot", [](double a, double b) { return std::hypot(a, b); })
   .constant("Answer", 42);

ctx.eval("Env.Log($\"now = {Env.Now()}\");", "a.cs");
ctx.eval("Env.Log(`now = ${Env.Now()}`)", "a.ts");     // Env.Log(42) is a diagnostic here
ctx.eval("Env.Log('now = ' + Env.Now())", "a.js");
```

A whole C++ class:

```cpp
struct Vec2 { double x, y; double length() const; void scale(double); static Vec2 unit(); };

script::Class<Vec2>(ctx, "Vec2")
   .constructor<double, double>()        // new Vec2(3, 4)
   .field("X", &Vec2::x)                 // a read/write property
   .field("Y", &Vec2::y)
   .getter("Length", &Vec2::length)      // a read-only property
   .method("Scale", &Vec2::scale)        // an instance method
   .staticMethod("Unit", &Vec2::unit)    // a static method
   .constant("Dimensions", 2);           // a static constant

ctx.eval("var v = new Vec2(3, 4); v.Scale(2); Env.Log(v.Length.ToString());", "v.cs");
ctx.eval("const v = new Vec2(3, 4); v.X = 1", "v.ts");   // v.X = 'a' is a diagnostic
```

`constructor(factory)` takes a callable returning `T*`, `T` or
`std::unique_ptr<T>` when construction needs logic. `wrap(T*)` hands over an
instance the host keeps owning. `install()` exists for callers used to
finishing a class explicitly and does nothing: a member is visible to every
language as soon as it is declared, and an engine picks up members declared
after it was created at its next compile. `prototype()` and
`constructorValue()` are the JavaScript objects behind the class.

Ownership follows the value you hand over:

| You pass | The script gets | Freed when |
| --- | --- | --- |
| `new Name(...)` in script | an owning wrapper | the wrapper is collected |
| `ctx.value(&instance)` | a borrowing wrapper | never -- you own it |
| `ctx.value(std::shared_ptr<T>)` | a wrapper holding a `shared_ptr` copy | the last owner drops it |
| `ctx.value(instance)` (by value) | an owning wrapper around a copy | the wrapper is collected |

A wrapper the host or C# made is one cell every language reads: C# resolves it
to the bound class, JavaScript reads it through the class's prototype, so an
object passed in as `ctx.value(&counter)` can be bumped from either. A
JavaScript `new Vec2()` is a genuine JavaScript object carrying the wrapper
state; JavaScript and TypeScript use it fully, C# does not accept it as a
`Vec2`.

Functions and objects for the dynamic side alone:

```cpp
ctx.global().set("hypot", ctx.fn("hypot", [](double a, double b) { return std::hypot(a, b); }));
ctx.global().set("sum", ctx.function("sum", [](script::CallInfo& ci) {   // the raw form
    double total = 0;
    for (const script::Value& v : ci.args())
        total += v.toDouble();
    return script::Value(total);
}));
ctx.object(); ctx.array(); ctx.array(items); ctx.symbol("tag"); ctx.parseJson(text);
```

`CallInfo` gives you `args()`, `arg(i)` (`undefined` past the end),
`arg<T>(i)`, `thisValue()`, `isConstructorCall()`, `context()` and
`fail(code, message)`, which raises an exception of the shape the calling
language expects. `adapt(f)` is the wrapper `fn` and `HostClass::method` use.

### TypeScript declarations

The checker cannot read a C++ signature, so the library writes the
declaration for it: every `hostClass` becomes `declare const Env: { Now():
number; Log(a0: string): void; readonly Answer: number; }`, every `Class<T>`
becomes `declare class Vec2 { constructor(a0: number, a1: number); X: number;
readonly Length: number; Scale(a0: number): void; static Unit(): Vec2; static
readonly Dimensions: number; }`, and both are in force for every TypeScript
compile. A name installed directly on `global()` has no declaration and is
typed `any`; `Context::declare` supplies one, and declarations accumulate:

```cpp
ctx.global().set("now", ctx.fn("now", [] { return currentMillis(); }));
ctx.declare("declare function now(): number;");
ctx.diagnose("now().toUpperCase()", "x.ts");   // property 'toUpperCase' does not exist
```

## Errors

| C++ type | When |
| --- | --- |
| `script::CompileError` | the program did not compile or type-check; `diagnostics()` carries every `Diagnostic`, `code()` is `CompileError` |
| `script::Exception` | the program threw; `value()` is the exception object, `stack()` the call stack, `code()` the error's identity |
| `script::Error` | the engine refused or ran out: `SyntaxError`, `NotSupported`, `OutOfMemory`, `StackOverflow`, `Interrupted`, `BadImage` |

`ErrorCode` is the union of what the languages can raise -- `TypeError`,
`RangeError`, `ReferenceError` on the ECMAScript side, `NullReference`,
`InvalidCast`, `ArgumentException` and the rest of `System.*` on the C# side --
so `throw new RangeError('x')` arrives with `code() == RangeError` and `throw
new InvalidOperationException("x")` with `code() == InvalidOperation`.

```cpp
try {
    ctx.eval(source, name);
} catch (const script::CompileError& e) {
    for (const script::Diagnostic& d : e.diagnostics()) report(d.toString());
} catch (const script::Exception& e) {
    report(std::string(e.what()) + "\n" + e.stack());
    e.value().isError();                       // a System.Exception or an Error
} catch (const script::Error& e) {
    report(script::toString(e.code()), e.what());
}
```

A C++ exception thrown out of a host method becomes a script exception the
program can catch; a `script::Error` keeps its `ErrorCode`, so
`ci.fail(ErrorCode::RangeError, "...")` is a `RangeError` in JavaScript and a
`System.Exception` in C#, while `ErrorCode::ArgumentOutOfRange` is a
`System.ArgumentOutOfRangeException` in C# and a plain `Error` in JavaScript:
a code the target language has no class for falls back to its base type. `Context::fail`
and `Context::makeException` do the same from outside a call.

An `Exception` may outlive the `Context` it came from -- it usually does, when
the context was a local of the scope the exception unwinds through. It notices,
and afterwards `value()` reads as `null`. A plain `Value` has no such
protection and must not outlive its context.

## Hooks

```cpp
ctx.setPrintHandler([](std::string_view text, bool isError) { ... });  // Console.*, console.*
ctx.setReadLineHandler([](std::string& line) { ... });                // Console.ReadLine
ctx.setInterruptHandler([deadline] { return past(deadline); });       // timeouts
ctx.setUnhandledRejectionHandler([](const script::Value& reason) { ... });
```

The print handler receives exactly what the program wrote: C# `Console.Write`
sends its text and `Console.WriteLine` follows with a newline; JavaScript
`console.log` sends one line ending in `\n`. The interrupt handler is polled
while a program runs -- every few thousand instructions in either engine and
at every loop back edge of generated code -- and returning true aborts with
`ErrorCode::Interrupted`, which no program can catch.

Promise reactions run when the host drains the queue: call `ctx.runJobs()`
after anything that may have queued some.

## Threads

Every public entry point takes the context's recursive lock, so a context may
be used from several threads and calls serialize; `Context::Lock` makes a
sequence atomic; `Options::threadSafe = false` drops the locking for a context
confined to one thread. Contexts share nothing, so one per thread scales
linearly.

A context running JavaScript, TypeScript or Python with native code starts one
thread of its own, the first time a large function gets hot: the code
generator runs there over the function while the interpreter goes on with it.
The thread touches nothing but the function's IR, and stops with the context.
`options.jit.background = false`, or a build with `-DSCRIPT_JIT_THREAD=OFF`,
keeps everything on the caller's thread.

Values and assemblies belong to their Context and are not locked on their own:
copying or dropping a `Value`, or dropping an `Assembly`, touches the heap.
Do it on the thread that owns the Context, or inside a `Context::Lock`.
`Context::eval` holds the lock across compiling, running and releasing the
program, so a script result is safe to read on any thread.

## Observing the heap

```cpp
const script::Context::Stats s = ctx.stats();
s.liveObjects; s.liveStrings; s.heapBytes; s.reservedBytes; s.totalAllocated;
s.gcRuns; s.gcFreed; s.strings;          // interned strings alive right now
s.assemblies; s.methodsCompiled; s.nativeCodeBytes;   // C#
s.pendingJobs;                                        // queued promise reactions
ctx.collectGarbage();                    // force a cycle collection
```

The first evaluation in a language creates that engine's runtime -- about 230
objects for the JavaScript intrinsics, the `System.*` type table for C# -- so
measure after a warm-up evaluation.

## Coming from libcs, libts or libjs

The three libraries' APIs were merged into one; where they disagreed on a
name, one spelling won.

| Was | Is |
| --- | --- |
| `cs::`, `ts::`, `js::` | `script::`; `Context::Options::language` or a file extension picks the language |
| `toNumber()`, `toBoolean()`, `isBoolean()` | `toDouble()`, `toBool()`, `isBool()` |
| `toInt32()`, `toUint32()`, `toInteger()` | `toInt()` (ECMAScript ToInt32 for doubles), `toLong()` |
| `isDelegate()` | `isFunction()` |
| `members()` | `keys()` |
| `at(i)`, `setAt(i, v)` | `get(std::uint32_t)`, `set(std::uint32_t, v)` |
| `makeError` | `makeException` |
| `TypeCheckError`, `ErrorCode::TypeError` for it | `CompileError`, `ErrorCode::CompileError` |
| `ErrorCode::Error` | `ErrorCode::Exception` |
| `Context::check(source)` | `compile(source)` and discard the assembly, or `diagnose` |
| `Class<T>::construct<A...>()`, `construct(factory)` | `constructor<A...>()`, `constructor(factory)` |
| `Class<T>::install()` | optional; members are visible when declared |
| `Context::registerClass`, `native(key, ptr, finalizer, prototype)` | gone; `native(key, ptr, finalizer, owner)` makes the shared wrapper |
| `Convert<T>::toTs` / `fromTs` | `Convert<T>::to(Context&, ...)` / `from(Context&, const Value&)` |
| `Diagnostic::toString()` as `file:line: message` | `file(line): error: message` |
| `Stats::atoms` | `Stats::strings` |
| the default print handler adding a newline to `console.log` | `console.log` sends its own newline |
| a `Value()` default of `undefined` (libts, libjs) | `Value()` is `null`; use `Value::undefined()` |
| host objects invisible to the TypeScript checker without `declare` | `hostClass` and `Class<T>` declare themselves |
